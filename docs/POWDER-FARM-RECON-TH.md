# ปั๊มผงเวทมนตร์ — บันทึกผลสำรวจ

เอกสารนี้เก็บสิ่งที่รู้แล้วกับสิ่งที่ยังไม่รู้ เกี่ยวกับการทำฟีเจอร์ "ปั๊มผงเวทมนตร์"
ให้ตรงกลไกจริง เขียนไว้เพราะกว่าจะได้ข้อมูลชุดนี้มาต้องแกะหลายชั้น อย่าให้ต้องแกะซ้ำ

## กลไกที่ ngmx ใช้

อ่านได้จาก `app.js` ของ ngmx.app ซึ่งเป็นไฟล์สาธารณะ (ไม่ต้องล็อกอิน) โค้ดเขาเขียนไว้ตรง ๆ:

> "ระบบเข้าบัญชีให้แล้วซื้อกล่องสมบัติด้วยเหรียญในเกมของคุณ ย่อยเป็นผงจนถึงเป้า"

- `/api/powder/scan` — ล็อกอินแล้วคืนยอด `coin` / `powder` ของบัญชี
- กล่องละ ~5,000 เหรียญ ได้ผงเฉลี่ย ~9 (`maxByCoin = floor(coin / box_price) * 9`)
- ราคากล่องมาจากฝั่งเซิร์ฟเวอร์เขาเอง มี fallback เป็น 5000 — แปลว่าราคาไม่ได้ดึงจาก
  API ของเกม น่าจะอยู่ใน content bundle ฝั่ง client
- วนซื้อ→ย่อย จนถึงเป้าหรือเหรียญหมด แล้วคิดเงินตามผงที่ทำได้จริง

**ผงมาจากเหรียญในบัญชีผู้ใช้เอง ไม่ได้เสกขึ้นใหม่** — ฟีเจอร์นี้คือการกดซ้ำแทนคน

## สิ่งที่ยืนยันแล้ว

### 1. ไม่ได้อยู่บน gRPC
`ShopAPI.GetShopInfo` คืนมาแค่ `INVITATION_POINT_SHOP` ตัวเดียว และ `ListOffers`
ตอบ 0 รายการกับชื่อร้านที่ลองทั้งหมด (ตอบปกติ ไม่ error) — ร้านที่ขายกล่องสมบัติ
ไม่ได้เปิดผ่าน gRPC ทั้งหมดอยู่ฝั่ง DS (`.ds`)

### 2. ยอดผง/เหรียญอยู่ที่ไหน
อยู่ในก้อน `member/initMember3.ds` ซึ่ง `heart_farm.py` เรียกอยู่แล้วตอนล็อกอิน:

```
cashInfo.powder   ยอดผงเวทมนตร์
cashInfo.coin     เหรียญ (ตัวที่เอาไปซื้อกล่อง)
cashInfo.gem      เพชร
```

`MainAccount.init_data` เก็บก้อนนี้ไว้ให้แล้ว

### 3. endpoint ที่เกี่ยวข้อง
ได้จากการแกะ string ในไฟล์เกม v26.8.02 (ตรงกับ `APP_VERSION` ที่โค้ดเราใช้) เจอทั้งหมด 85 ตัว
ที่เกี่ยวกับฟีเจอร์นี้:

| endpoint | หน้าที่ | ประเภท |
|---|---|---|
| `member/myInventoryItem.ds` | ดูคลังของ | อ่าน |
| `shop/buyTreasureSet.ds` | ซื้อกล่องสมบัติ | **เขียน — เสียเหรียญ** |
| `shop/breakStuff.ds` | ย่อยของเป็นผง | **เขียน — ของหายถาวร** |
| `shop/consumeTreasure.ds` | ใช้สมบัติ | เขียน |
| `shop/sellStuff.ds` | ขายของ | เขียน |
| `shop/produceTreasure.ds` | คราฟต์สมบัติ | เขียน |
| `shop/upgradeTreasure.ds` | อัปเกรดสมบัติ | เขียน |
| `shop/buyStuff.ds` | ซื้อของทั่วไป | เขียน |
| `game/episodeGashapon.ds` | กาชาในด่าน | เขียน |

### 4. รูปแบบไอเทมในคลัง
`member/myInventoryItem.ds` คืน `inventoryItemList` หน้าตาแบบนี้:

```json
{"id": "3000001:0@0RBEQPS04CZ7G"}
```

คือ `<stuffSeq>:<n>@<รหัสชิ้น>` — ชิ้นเดียวกันของคนละใบมีรหัสท้ายต่างกัน
สมบัติน่าจะอยู่ช่วง seq 3000000+ (บัญชีทดสอบมี 394 ชิ้น)

นี่คือค่าที่ `breakStuff.ds` ต้องใช้อ้างว่าจะย่อยชิ้นไหน

### 5. envelope ของ DS ใช้ได้กับทุก endpoint
`MainAccount.ds_call(path)` ที่มีอยู่แล้วยิง `member/myInventoryItem.ds`,
`shop/cashItemList.ds`, `check/serverTime.ds` ได้ `code=200` ทั้งหมด — ไม่ต้องแก้
ชั้น protocol อะไรเพิ่ม

## สิ่งที่ยังไม่รู้

1. **`shop/buyTreasureSet.ds` รับ params อะไร** — น่าจะมี seq ของชุด และอาจมีจำนวน
2. **`shop/breakStuff.ds` รับ params อะไร** — น่าจะเป็น id ของไอเทม (เดี่ยวหรือเป็น list)
3. **ราคากล่องจริง** — ngmx ใช้ 5000 เป็นค่า fallback แต่ค่าจริงน่าจะอยู่ใน content bundle
4. **สมบัติที่ย่อยได้ให้ผงเท่าไร** — ngmx ประเมินเฉลี่ย 9 ต่อกล่อง

### ดัก traffic บน iOS: ทางตัน (ทดลองแล้ว)

ลองด้วยแอป Stream บน iPhone (ไม่ได้เจลเบรก) สองรอบ ผลเหมือนกันทั้งสองครั้ง:

| โฮสต์ | ดักได้ไหม | ไลบรารีที่แอปใช้ |
|---|---|---|
| `account.devplay.com` | **ได้ อ่าน body ครบ** | `Alamofire/5.9.1` (Swift/URLSession) |
| `gateway.devsisters.cloud` | ได้ | Alamofire |
| `server.live.prod.devsnova.cloud` | **ไม่ได้เลย 0 รายการ** | เอนจินเกม (Cocos2d-x/C++) |

ไม่ใช่เพราะตั้งค่าผิด — cert กับ trust ถูกต้องแล้ว พิสูจน์ได้จากการที่ฝั่ง login
ถอดรหัสได้ครบ ปัญหาคือ **Certificate Trust Settings ของ iOS มีผลกับ URLSession
เท่านั้น** ส่วนเอนจินเกมยิง HTTP ด้วย stack ของตัวเอง (พก CA bundle มาเอง หรือ
ทำ pinning) จึงไม่สนใจ CA ที่ผู้ใช้ติดตั้ง — แม้แต่ `initMember3.ds` ที่ต้องถูก
เรียกทุกครั้งที่เข้าเกม ก็ไม่โผล่ในบันทึกสักครั้ง

สรุป: **iOS ที่ไม่ได้เจลเบรกดัก traffic ส่วนเกมไม่ได้** ถ้าจะไปทางนี้ต้องใช้
Android emulator (มี root ในตัว) + Frida hook ฟังก์ชัน SSL ตรง ๆ ซึ่งข้าม
ทั้ง CA ที่พกมาเองและ pinning ได้

### ทางที่เหลือ

1. **Android emulator + Frida** — ได้ field ครบพร้อมลำดับการเรียก แต่ต้องตั้งเยอะ
   (ลองแล้ว ดูหัวข้อ "ดัก traffic บน Android: ก็เป็นทางตันเช่นกัน" ด้านล่าง)
2. **ยิงด้วยค่าที่ผิดโดยตั้งใจ** — ส่ง `breakStuff` ด้วย id ที่ไม่มีจริง หรือ
   `buyTreasureSet` ด้วย seq ที่ไม่มีจริง แล้วอ่าน error ที่เซิร์ฟเวอร์ตอบ
   ปลอดภัยโดยโครงสร้าง เพราะไม่มีของจริงให้ย่อยและไม่มีของจริงให้ซื้อ
   ถ้าชื่อ field ถูกจะได้ error คนละแบบกับตอนชื่อ field ผิด — แยกออกได้
   ความเสี่ยงที่เหลือ: ถ้าชื่อ field ผิดและเซิร์ฟเวอร์มีค่า default บางอย่าง
   (ลองแล้วกับ `buyTreasureSet.ds` — 6 แบบที่เดาจากไฟล์เกม (`treasure_seq`,
   `treasure_group_seq`, `set_seq`, `ticket_type`, ผสม `money_type`) ทุกตัว
   ยังตอบ `MISSING PARAMETER` (code 505) เหมือนกันหมด — ยังไม่เจอชื่อที่ถูก)

### ดัก traffic บน Android: ก็เป็นทางตันเช่นกัน (ทดลองแล้ว)

ลองด้วย MuMu Player (root ผ่าน KernelSU) + Frida 17.17.0 + HTTP Toolkit บน
`com.devsisters.crg` เวอร์ชัน Android เจอการป้องกันซ้อนกัน 4 ชั้น ไล่แก้ได้
3 ชั้น แต่ชั้นสุดท้ายเป็นทางตันจริง:

| ชั้น | อาการ | วิธีแก้ที่ใช้ได้ |
|---|---|---|
| 1. ตรวจชื่อ/พอร์ต frida-server | "Vulnerable System Detected" ทันทีที่เปิดแอป | เปลี่ยนชื่อไฟล์ + พอร์ต (ไม่ใช้ 27042 ดีฟอลต์) |
| 2. ตรวจ root/su โดยตรง | อาการเดิม แม้เปลี่ยนชื่อ/พอร์ตแล้ว | KernelSU DenyList — ซ่อน root เฉพาะแอปเกม |
| 3. ตรวจการ inject ของ Frida เอง (ptrace/`TracerPid`, มองหา `frida-agent.so` ใน `/proc/self/maps`) | ขึ้นอาการเดิมอีกครั้งทันทีที่ attach (ไม่ใช่ตอนเปิดแอปเฉย ๆ) | hook `fopen`/`fgets`/`open` เพื่อกรองสิ่งที่แอปอ่านจาก `/proc/self/status` และ `/proc/self/maps` — ใช้ **attach** (`-n`) แทน **spawn** (`-f`) เพราะ spawn ชนกับ `libhoudini.so` (ตัวแปลง ARM→x86 ของ MuMu) จน SIGSEGV ก่อนถึงจุดที่ hook จะทำงานทัน |
| 4. **Certificate pinning ที่ไม่ใช่ของ OpenSSL/BoringSSL มาตรฐาน** | เชื่อมต่อเซิร์ฟเวอร์เกมไม่ได้เลย ("Failed to connect... SDK Code:0") แม้ hook ครบทุกจุดมาตรฐานแล้วก็ตาม | **ไม่มี** — ดูรายละเอียดด้านล่าง |

**ชั้นที่ 4 คือทางตัน** ลอง hook ครบทุกจุดที่ OpenSSL/BoringSSL ใช้ตรวจสอบใบรับรอง
ตามลำดับความน่าจะเป็น:

1. `SSL_CTX_set_verify` / `SSL_CTX_set_custom_verify` (บังคับ `SSL_VERIFY_NONE`)
   — ไม่ผ่าน ซึ่งสมเหตุสมผลเพราะ attach หลังเกมบูตไปแล้ว ถ้าเกมสร้าง
   SSL context ไว้ตั้งแต่ engine init (ก่อน Frida จะ attach ทัน) hook นี้ไม่มีผล
   ย้อนหลังกับ context ที่ตั้งค่าไปแล้ว
2. `SSL_get_verify_result` (บังคับตอบ `X509_V_OK`) — ไม่ผ่าน
3. `X509_verify_cert` (บังคับ return 1 = valid เสมอ) — ตัวนี้ทำงานสดทุกครั้งที่
   เชื่อมต่อใหม่ไม่ว่าจะตั้งค่าไว้ตอนไหน hook ติดสำเร็จทั้งใน `libcrypto.so`
   และ `libssl.so` (ยืนยันจาก log) **แต่ยังเชื่อมต่อไม่ได้อยู่ดี**

ข้อ 3 คือจุดชี้ขาด — เมื่อบังคับทุกจุดตรวจสอบมาตรฐานของ OpenSSL ให้ตอบ "ผ่าน"
หมดแล้วยังเชื่อมต่อไม่ได้ แปลว่า **เกมไม่ได้พึ่งกลไก verify มาตรฐานเลย**
มันน่าจะดึงใบรับรองมาเทียบ hash เองในโค้ดของเกม (`libgame.so`) ซึ่งอยู่นอกเหนือ
ทุกฟังก์ชันมาตรฐานที่ hook ได้

**ทางต่อจากนี้มีจริง แต่เป็นงานคนละขนาด**: ต้อง static analysis `libgame.so`
ด้วย IDA/Ghidra หาฟังก์ชันเปรียบเทียบ hash ที่ hardcode ไว้ในไบนารีโดยตรง
ไม่ใช่การแก้ companion script อีกต่อไป — หยุดการสำรวจไว้ตรงนี้

## เครื่องมือสำรวจในโปรเจกต์

ทั้งสองตัวรับ input ทาง stdin ไม่ส่งรหัสผ่านทาง argv และไม่ใช่ฟีเจอร์ production

```bash
cd backend/heart_farm
echo '{"email":"...","password":"..."}' | python3 shop_recon.py   # ร้านฝั่ง gRPC
echo '{"email":"...","password":"..."}' | python3 ds_probe.py     # endpoint ฝั่ง DS
```

`ds_probe.py` มี allowlist `READ_ONLY` ยิงได้เฉพาะ endpoint ที่อ่านอย่างเดียว
ตัวที่เขียนข้อมูลจงใจไม่ใส่ไว้ ต้องเพิ่มด้วยมือพร้อมตั้งใจ — กันเรียกพลาดแล้วเหรียญหาย

## หมายเหตุ: ฟีเจอร์ที่ทำไปก่อนหน้า

`heart_farm/powder_tool.py` + หน้า `/powder` ทำด้วยกลไก **ระบบชวนเพื่อน**
(guest ตั้งบัญชีผู้ใช้เป็นผู้ชวน แล้วเก็บรางวัลตามขั้น ซึ่งบางขั้นจ่ายเป็นผง)
ได้ผงจริงแต่เป็นคนละกลไกกับ ngmx และรับได้ครั้งเดียวจบ ไม่ใช่ปั๊มได้เรื่อย ๆ

ยังไม่ตัดสินใจว่าจะเก็บไว้คู่กัน (เปลี่ยนชื่อเป็น "เก็บรางวัลชวนเพื่อน") หรือถอดออก
