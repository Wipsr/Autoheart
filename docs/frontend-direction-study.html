ความจริง 6 ข้อจาก Backend ที่บังคับรูปร่างหน้าบ้าน

ก่อนวาดอะไร ต้องยอมรับก่อนว่าระบบนี้มีลักษณะเฉพาะที่ออกแบบหนีไม่ได้ — และหลายข้อ กลับเป็น “ของดี” ที่หน้าบ้านปัจจุบันยังไม่ได้ใช้ประโยชน์

01 · เครื่องเดียว คิวเดียว worker รันที่ replicas = 1 งานไม่ซ้อนกัน ทุกคนต่อคิวเส้นเดียว มี queue_position และ estimated_wait_minutes จริง → ความโปร่งใสของคิวคือจุดขาย ไม่ใช่ข้อจำกัดที่ต้องซ่อน
02 · เครดิต = หัวใจ ไม่มีสกุลเงินกลาง เติมด้วยซองแล้วได้ “หัวใจ” มาถือไว้ ตัดตอนสั่งงานผ่าน deduct_user_hearts → หน้าบ้านควรพูดภาษากระเป๋าเงิน ไม่ใช่ภาษาตะกร้าสินค้า
03 · งานเป็นชุดได้ถึง 50 POST /api/jobs/create รับ credentials[] ได้ 1–50 รายการ แต่ละอันกลายเป็น 1 job → ผู้ใช้ตัวจริงบางกลุ่มคือคนรัน 20 ไอดีต่อรอบ ไม่ใช่คนซื้อทีละแพ็ค
04 · มีเครื่องมือฟรี 3 ตัว /api/account/inspect (ดูของในคลัง), /api/friends/list + delete, /api/credentials/verify — ไม่ตัดเครดิต → เป็นประตูดึงคนเข้าเว็บได้ฟรี ๆ
05 · สตรีมสดครบ ws/jobs/{id} ส่ง hearts_collected, session x/y, progress %, log ทีละบรรทัด และ ws/queue ส่งความเคลื่อนไหวคิว → รองรับ UI ที่ “มีชีวิต” ได้เต็มที่
06 · หน้าสาธารณะไม่ต้องล็อกอิน /api/public/queue-stats, /api/public/site-config, /api/promotions/active เปิดโล่ง → หน้าแรกโชว์ของจริงได้ ไม่ต้องเป็นโบรชัวร์
ของเดิมทำอะไรอยู่ — sidebar 7 เมนู + การ์ดสถิติ 3 ใบ + wizard ซื้อแบบหลายขั้น บนพื้นกรมท่ากับชมพู เป็นทรง SaaS dashboard มาตรฐาน ทั้งสามทิศทางข้างล่างนี้ จงใจไม่กลับไปที่ทรงนั้นเลย — ทั้งเรื่องการนำทาง ความหนาแน่น และวิธีที่ผู้ใช้ “สั่งงาน”

ได้อะไร

  • งาน 20 ไอดีจบใน ~15 วินาที เทียบกับ wizard เดิมที่ต้องวนหลายรอบ

เสียอะไร / เสี่ยงตรงไหน

  • ลูกค้าใหม่ที่ไม่คุ้น terminal จะกลัวจอ — ต้องมีโหมดชิปและตัวอย่างพร้อมแตะ
  • มือถือคือจุดอ่อน แม้จะแก้ด้วยชิปแล้วก็ยังฝืด
  • Accessibility ต้องทำจริงจัง (aria-live กับสตรีมที่วิ่ง)
  • ถ้าฐานลูกค้าคือคนซื้อทีละแพ็ค ทิศทางนี้จะเกินความจำเป็น

คิวสาธารณะ คนที่ยังไม่สมัครเห็นคิวจริงเคลื่อนไหว = หลักฐานว่าระบบทำงานอยู่ แทนหน้า landing ที่โม้อย่างเดียว /api/public/queue-stats มีแล้ว
ETA เดินจริง นาฬิกาถอยหลังต่อเนื่อง ปรับตัวเมื่อคิวหน้าเสร็จเร็ว/ช้ากว่าคาด ไม่ใช่ตัวเลขค้าง estimated_wait_minutes + tick ฝั่ง client มีแล้ว
โหมดดูเต็มจอ จอเดียวโชว์ตัวนับหัวใจตัวใหญ่ + log วิ่ง เปิดค้างไว้ดูเพลิน ๆ ได้ (คนกลุ่มนี้มีจริง) ws/jobs/{id} มีแล้ว
สลับลำดับงานตัวเอง มี 5 งานในคิว อยากให้ไอดีนี้ขึ้นก่อน — ลากสลับได้เฉพาะในกลุ่มงานของตัวเอง ไม่กระทบคนอื่น เสนอ PATCH /api/jobs/reorder (มี resequence ฝั่ง admin อยู่แล้ว) ต้องเพิ่ม
เตือนเมื่อใกล้ถึงคิว ปิดแท็บไปทำอย่างอื่นได้ ระบบเตือนตอนเหลือ 5 นาที Web Push / Notification API + ws/queue ฝั่งหน้าเว็บ
ปิดชื่อเสมอ การ์ดคนอื่นโชว์แค่ 3 ตัวแรกของอีเมล — โปร่งใสได้โดยไม่แลกความเป็นส่วนตัว ต้องปิดฝั่ง server ไม่ใช่ปิดด้วย CSS ต้องเพิ่ม

ได้อะไร

  • เปลี่ยนข้อจำกัด “เครื่องเดียว” ให้กลายเป็นจุดขายเรื่องความโปร่งใส
  • ลดคำถาม “คิวถึงเมื่อไหร่” ที่กินเวลาแอดมินมากที่สุด
  • หน้าแรกกับหน้าใช้งานเป็นหน้าเดียวกัน — ไม่ต้องดูแลสองโลก
  • เป็นภาพจำที่แคปหน้าจอไปโพสต์ต่อได้

เสียอะไร / เสี่ยงตรงไหน

  • ความเป็นส่วนตัว — ต้องปิดชื่อฝั่ง server ให้แน่นก่อนปล่อย
  • คิวยาว 40 งานจะรก ต้องออกแบบการยุบกลุ่มให้ดี
  • Motion เยอะ = งาน perf จริง และต้องเคารพ prefers-reduced-motion
  • มือถือต้องออกแบบซ้ำอีกรอบ ไม่ใช่แค่ย่อ
  • วันที่คิวว่างเปล่า หน้าจะดูเหงา — ต้องมีสถานะว่างที่ดูดี

ฟังก์ชันทำอะไรต่อกับอะไรสถานะ
สมุดบัญชีเล่มเดียว รวมเติมเงิน ตัดหัวใจ และคืนหัวใจ ไว้ในเส้นเวลาเดียว ตอบคำถาม “หัวใจหายไปไหน” ได้ในหน้าจอเดียว รวม /api/topup/history + /api/jobs/mine ฝั่ง client ฝั่งหน้าเว็บ
ติดตามแบบพัสดุ ห้าสถานะที่คนไทยอ่านออกทันที map ตรงกับ queued / validating / processing / completed / failed JobStatus + ws/jobs/{id} มีแล้ว
สลิปงานเสร็จ งานจบแล้วได้การ์ดสรุป เซฟเป็นรูปหรือแชร์ต่อได้ — ลูกค้าใช้ยืนยันกับตัวเอง ร้านใช้ส่งให้ลูกค้าต่อ วาดด้วย Canvas ฝั่ง client จาก /api/jobs/{id} ฝั่งหน้าเว็บ
ไอดีที่บันทึกไว้ เก็บเฉพาะอีเมล/ชื่อเล่นไว้ในเครื่อง เพื่อไม่ต้องพิมพ์ซ้ำ — ไม่เก็บรหัสผ่าน ทั้งในเครื่องและบนเซิร์ฟเวอร์ localStorage เท่านั้น (backend ไม่มีที่เก็บ และไม่ควรมี) ฝั่งหน้าเว็บ
แท็บ “บริการ” ยกเครื่องมือฟรีขึ้นเป็นแท็บหลัก: เช็คของในไอดี · จัดการเพื่อน — เป็นเหตุผลให้เปิดแอปแม้วันที่ไม่ซื้อ /api/account/inspect, /api/friends/* มีแล้ว
รายการเดินบัญชีจากเซิร์ฟเวอร์ ระยะยาวควรมี endpoint เดียวที่เรียงมาให้แล้ว แทนการต่อสองแหล่งฝั่ง client เสนอ GET /api/ledger ต้องเพิ่ม

ได้อะไร

  • ตรงกับพฤติกรรมจริง — คนจ่ายซองอั่งเปาอยู่บนมือถืออยู่แล้ว
  • เส้นทางซื้อสั้นที่สุดในสามทิศทาง แปลงเป็นยอดขายได้ดีที่สุด
  • ธีมสว่างทำให้ต่างจากเว็บฟาร์มเจ้าอื่นที่มืดเหมือนกันหมด
  • สลิปแชร์ได้ = การตลาดฟรีจากลูกค้า

เสียอะไร / เสี่ยงตรงไหน

  • คนรัน 20 ไอดีต่อรอบจะอึดอัด — ต้องมีโหมดชุดแยกต่างหาก
  • เดสก์ท็อปกลายเป็นพลเมืองชั้นสอง ต้องออกแบบเพิ่ม ไม่ใช่ยืดให้เต็มจอ
  • ภาษากระเป๋าเงินอาจทำให้เข้าใจผิดว่าถอนเป็นเงินคืนได้ — ต้องเขียนให้ชัด
  • หน้า Admin ไม่เข้ากับแนวนี้เลย ต้องใช้ภาษางานออกแบบคนละชุด

05

สิ่งที่ backend ยังไม่มี ถ้าเลือกทิศทางนั้น

ทุกอย่างที่เหลือใช้ของที่มีอยู่ได้เลย รายการนี้คือส่วนที่ต้องคุยกับฝั่ง backend ก่อน เรียงจากคุ้มที่สุดลงไป

สิ่งที่ต้องเพิ่มทำไมถึงต้องมีจำเป็นกับขนาดงาน
POST /api/jobs/create?dry_run=true ตอนนี้การตรวจไอดีกับการตัดเครดิตอยู่ในคำสั่งเดียวกัน ทำให้หน้าบ้านโชว์ยอดจริงก่อนผู้ใช้ยืนยันไม่ได้ ต้องเดาเอง A · C (และดีกับ B) เล็ก
ยืนยันพฤติกรรมการคืนเครดิต ต้องรู้ชัดว่ายกเลิกงานสถานะ queued แล้วคืนหัวใจครบหรือไม่ ก่อนจะสัญญาปุ่ม “ยกเลิก / ถอย” กับผู้ใช้ ทั้งสาม ตรวจอย่างเดียว
ปิดชื่อในข้อมูลคิวสาธารณะ จะโชว์คิวคนอื่นได้ ต้องมั่นใจว่า payload ไม่มีอีเมลเต็มหลุดออกมา — ปิดด้วย CSS ไม่นับ B เล็ก
PATCH /api/jobs/reorder ให้ผู้ใช้สลับลำดับเฉพาะงานของตัวเอง โดยไม่แซงคิวคนอื่น (ฝั่ง admin มี resequence อยู่แล้ว) B กลาง
GET /api/ledger รวมเติม/ตัด/คืน เรียงเวลามาให้ในครั้งเดียว แทนที่หน้าบ้านจะต่อสองแหล่งแล้วเรียงเอง C กลาง
สรุปสถิติของผู้ใช้ หัวใจที่เก็บได้รวม / งานสำเร็จ / เวลารอเฉลี่ย — ใช้ทำหน้า “ฉัน” และสลิปให้มีน้ำหนัก C (ทางเลือกของ A · B) เล็ก
06

ถ้าให้เลือกให้

ข้อเสนอของผม

สามทิศทางนี้ไม่ได้ตั้งใจให้เลือกมาหนึ่งแล้วทิ้งสอง — เพราะแต่ละอันชนะคนละสนาม ทางที่คุ้มที่สุดคือ ใช้ C เป็นฐาน แล้วยืม B มาทำหน้าสาธารณะ และเก็บ A ไว้เป็นโหมดขั้นสูง

  1. ฐานคือ C — ลูกค้าส่วนใหญ่อยู่บนมือถือและจ่ายด้วยซองอยู่แล้ว เส้นทางซื้อสั้นที่สุดคือสิ่งที่กระทบรายได้ตรงที่สุด
  2. หน้าแรกคือ B — เอาสายพานสดไปเป็นหน้าที่คนยังไม่ล็อกอินเห็น ใช้ endpoint สาธารณะที่มีอยู่แล้ว ไม่ต้องรออะไร และแก้ปัญหา “จะเชื่อได้ยังไงว่าไม่โกง” ได้ดีกว่าข้อความโฆษณาใด ๆ
  3. A เป็นโหมด ไม่ใช่เว็บทั้งเว็บ — เปิดด้วย ⌘K หรือปุ่มเดียวสำหรับคนรันหลายไอดี ได้ประโยชน์ของ A โดยไม่ผลักลูกค้าใหม่ทิ้ง
  4. Admin แยกโลก — 38 endpoint ฝั่ง admin ต้องการความหนาแน่นสูงและตารางล้วน ไม่ควรใช้ภาษาการออกแบบเดียวกับหน้าลูกค้า ควรทำเป็นสตัดดี้แยกอีกฉบับ

ถ้าอยากได้อันไหนลงลึกต่อ — wireframe ทุกหน้าจอ, ระบบดีไซน์โทเคน, หรือสเปกส่งต่อให้ dev — บอกได้ว่าเอาทิศทางไหน แล้วผมทำต่อให้เต็มฉบับ

หมายเหตุเรื่องขอบเขต — เอกสารนี้ไม่มีการแก้ไฟล์ใด ๆ ใน frontend/ หรือ backend/ ตามที่ตกลงกันไว้ ทุกอย่างที่เห็นเป็นภาพจำลองที่วาดขึ้นในเอกสาร ไม่ใช่โค้ดที่รันได้ และ endpoint ทุกตัวที่อ้างถึงมาจากการอ่านซอร์สจริงของ backend
